## Project Title

**CardioTwin India: a wearable and EHR research prototype for 7-day cardiovascular risk**

## Problem statement and healthcare use case

Hypertension and related risk factors can change over time. CardioTwin explores whether longitudinal wearable summaries combined with a synthetic patient profile can flag a simulated high-risk cardiovascular anomaly in the following seven days for hypertensive or otherwise high-risk adults in India. It is a research and demonstration prototype, not a clinical device, validated risk calculator, or substitute for medical advice. Alerts must never be used to diagnose, treat, or triage a real person.

## Technical stack, AI/ML model or framework details

Python 3.10+, pandas, NumPy, scikit-learn, XGBoost, PyTorch, Streamlit, and Plotly. Logistic regression and XGBoost baselines operate on weekly summary features. The hybrid model uses an MLP for static EHR features, a 1D CNN followed by a GRU for the 7-day wearable sequence, and a sigmoid fusion head. Patient-level train/validation/test partitions, AUROC, AUPRC, sensitivity at 10% FPR, and Brier score are implemented. The dashboard includes a personalized 14-day baseline versus 7-day drift view and a branching 14-day simulator with bootstrap ranges. Because outcomes are generated by explicit heuristics, reported metrics measure recovery of those rules only.

## Data & Ethics

This repository uses **synthetic data only**. No real patient data or PHI is collected or distributed. The built-in generators create synthetic EHR-like profiles and simulated wearable streams; the demo does not download external data. Synthea is cited as an optional way to generate synthetic FHIR/CSV records, not as the source of the included rows. Synthea is an open-source synthetic patient generator (Apache-2.0): https://github.com/synthetichealth/synthea. If you add another dataset later, check its license, consent, permitted use, and de-identification conditions before inclusion. This project is designed to avoid PHI and follow privacy-by-design principles; it does not establish DPDP Act or HIPAA compliance.

The target is a **rule-generated proxy label**, not a clinical event. It does not represent observed myocardial infarction, stroke, or other diagnosis. The threshold rules below are illustrative and are not validated medical criteria. Synthetic correlations can create misleadingly high scores. No clinical performance, safety, fairness, calibration, or generalizability claim is made.

## Data and label rules

`python run_demo.py --generate-only` writes a synthetic cohort. `data/ehr_synthetic/generate.py` creates demographic, diagnosis, medication, blood-pressure, BMI, and lab features. `data/wearable/generate.py` creates a configurable hourly HR, HRV, sleep stage, sleep efficiency, step count, and systolic BP stream with diurnal patterns and patient risk differences. Wearable dates and day aggregation use India Standard Time. Missing sensor values are forward-filled only; missingness flags are retained by the sequence model.

The labeler marks a 7-day window positive if, on any day in the following week, at least two of the following occur: resting HR ≥100 bpm or ≥20% over that patient's prior-week mean; nocturnal HRV <20 ms or ≥30% below baseline; sleep <5 hours; systolic BP ≥160 mmHg (when present). This is deliberately a transparent synthetic anomaly rule. It is not a validated definition of cardiovascular risk and does not estimate real-world event probability.

## Personalized baseline and Twin Drift

The dashboard compares the latest 7 adequately covered days with the preceding 14 days for the selected virtual patient. It reports per-signal baseline and recent medians, absolute changes, and sustained deviations using robust within-patient spread plus conservative display floors. Coverage is shown separately; at least 21 simulated days are needed. These heuristics describe change in a synthetic history and are not clinical thresholds or explanations of the model.

## Branching Futures Simulator

The simulator bootstraps recent synthetic days 30 times to draw three 14-day paths: continue the current pattern, gradually add up to 0.5 simulated sleep hours/night, or gradually add up to 15% simulated steps/day. For each path, the existing model is rescored on rolling seven-day inputs and the chart shows its median response with a 10th–90th percentile range. This is a reproducible input simulation, not a causal estimate of an intervention's effect and not a forecast of real clinical events.

## Evaluation snapshot

The values below are a **previous 180-patient, 14-day baseline run** with a 36-patient holdout and one 7-day input window per patient. They are recorded for transparency and are not results from the current 30-day default. Results measure only agreement with synthetic proxy labels:

| Model | AUROC | AUPRC | Sensitivity at 10% FPR | Brier score |
| --- | ---: | ---: | ---: | ---: |
| Logistic regression | 0.462 | 0.636 | 0.043 | 0.263 |
| XGBoost | 0.555 | 0.685 | 0.217 | 0.252 |
| CNN-GRU hybrid | 0.502 | 0.724 | 0.261 | 0.242 |

The proxy-label prevalence was 57.8%. These results do not establish clinical performance. AUROC is near chance, and the holdout is small; use this run to demonstrate the pipeline, not to claim a validated predictor. A fresh run also reports four-fold patient-grouped baseline cross-validation using development patients only, alongside a separate grouped holdout. Overlapping windows are never split across patients.

## Installation and use

Windows PowerShell:

```powershell
python3.14 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python run_demo.py --patients 300 --days 30 --epochs 12 --launch-dashboard
```

After updating from an earlier project version, rerun the full demo command to regenerate `artifacts/hybrid.pt` and its matching CSVs. Older checkpoints are intentionally rejected because their time-zone and missing-data preprocessing differs.

For separate steps, run `python run_demo.py --generate-only --patients 300 --days 30`, then `python -m src.training.train --patients 300 --days 30`, `python -m src.inference.predict --patient P0001`, and `python -m streamlit run src/dashboard/app.py` from the project root with the virtual environment activated. Use `python3.14` instead of `py` on systems where the Python launcher is unavailable.

To generate synthetic Synthea records instead, follow its official [Quick Start](https://github.com/synthetichealth/synthea#quick-start) and export FHIR or CSV. The included pipeline does not require Synthea or a network connection.

`python run_demo.py` generates data, trains compact logistic regression, XGBoost and hybrid models, writes model artifacts and example predictions, then prints the dashboard command. Use `--launch-dashboard` to start Streamlit after training. The default creates 300 virtual patients over 30 days to provide multiple overlapping windows per patient; the patient remains the unit of separation for train, validation, and holdout splits. More windows do not mean more independent patients. CPU runtime depends on hardware and first-time dependency installation; GPU is optional.

## Limitations and intended use

The generators encode assumptions chosen for demonstration. They do not model the diversity of Indian populations, device measurement error, missingness, clinical workflows, or actual event prevalence. Proxy-label metrics are not evidence of clinical validity. Before any real-world research, obtain appropriate ethics review, lawful data access, informed governance, clinical partners, external validation, bias analysis, calibration, safety testing, and regulatory advice.
